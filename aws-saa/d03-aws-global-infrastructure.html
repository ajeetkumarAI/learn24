02Regions, Availability Zones and edge locations

AWS groups its data centres like this:

PieceWhat it isIndia example
Regiona separate geographic area; your data stays there unless you move itap-south-1 Mumbai, ap-south-2 Hyderabad
Availability Zoneisolated location(s) inside a Region; spread your servers over 2+ AZsap-south-1a, 1b, 1c
Edge locationsmall sites in many cities that cache content close to users (CloudFront)Mumbai, Delhi, Chennai, Bengaluru, Hyderabad, Kolkata and more
🏦

Like a bank’s branches. A Region is a city; each AZ is a separate branch building in that city with its own power backup. If one branch floods, the others keep working. Edge locations are ATMs placed close to customers for quick service.

Correction to a common myth: you may read “AWS has 99.9999999% availability”. That number is actually about Amazon S3 durability (99.999999999%, “11 nines”: data is almost never lost). Availability (being online) depends on each service and on your design; for example EC2’s promise (SLA) is 99.99% when you run across multiple AZs.

🎯 Exam corner
  • Region = geographic area; AZ = one or more isolated data centres in a Region; edge location = CloudFront cache near users.
  • High availability = deploy across multiple AZs. Disaster recovery = across multiple Regions.
  • Choose a Region by: compliance/data residency, latency to users, service availability, price.

05Summary

  • AWS = Amazon Web Services: 200+ on-demand services, pay-as-you-go.
  • Region (e.g. Mumbai) contains 3+ Availability Zones; each AZ is one or more isolated data centres.
  • Edge locations cache content near users (CloudFront).
  • Choose a Region by compliance, latency, service availability and cost.
  • “11 nines” is S3 durability, not overall AWS availability.
