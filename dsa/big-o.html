Big-O & Complexity

⏱ 16 min🎬 Interactive chart💻 Python · Java · C++ · JavaScript

How to measure an algorithm before you run it: time and space complexity, common growth rates, and how to read constraints in an interview.

Why complexity matters

Two programs can give the same answer and still be wildly different: one finishes in a millisecond, the other runs for an hour. Big-O notation describes how the work grows as the input size n grows, ignoring constant factors and small terms. It is the language every coding interview uses.

Rule of thumb: about 10⁸ simple operations per second. If n = 10⁵, an O(n²) solution does 10¹⁰ operations, which is far too slow. O(n log n) does about 1.7 million, which is instant.

The common growth rates

Big-O Name Typical example n = 10⁵ feels
O(1) Constant Array index, hash-map lookup instant
O(log n) Logarithmic Binary search, balanced BST lookup instant
O(n) Linear One pass over an array, two pointers, sliding window instant
O(n log n) Linearithmic Merge sort, heap of size n, sort + scan instant
O(n²) Quadratic All pairs, bubble sort ~10 s (too slow)
O(2ⁿ) Exponential All subsets, naive recursion only for n ≤ 20–25
O(n!) Factorial All permutations only for n ≤ 10

Reading constraints like a pro

Interviewers hint at the expected complexity through the input size:

  • n ≤ 10 → O(n!) or O(2ⁿ) backtracking is fine
  • n ≤ 20 → O(2ⁿ) bitmask or backtracking
  • n ≤ 500 → O(n³) DP
  • n ≤ 5000 → O(n²)
  • n ≤ 10⁵ – 10⁶ → O(n log n) or O(n)
  • n ≥ 10⁹ → O(log n) or O(1) (math or binary search on the answer)

How to compute Big-O

  1. Loops multiply: a loop inside a loop over n is O(n²).
  2. Sequential steps add, and you keep the biggest: O(n) + O(n log n) = O(n log n).
  3. Halving the problem each step gives O(log n).
  4. Recursion: count the nodes of the recursion tree × the work per node. Two branches with depth n gives O(2ⁿ).
  5. Space counts extra memory: arrays, hash maps, and the recursion stack (depth h means O(h) space).

    s = 0
    for x in a: s += x
    return s

    return sum(1 for i in range(len(a)) for j in range(i + 1, len(a)) if a[i] + a[j] == k)

Amortised complexity

Appending to a dynamic array (Python list, Java ArrayList, C++ vector) is occasionally O(n), when it has to grow. Over many appends the total is still O(n), so each append is amortised O(1). The same argument explains why a monotonic stack or a sliding window is O(n): every element is pushed and popped at most once.

Common mistakes

  • Forgetting that s[i:j] slicing or string concatenation in a loop copies data (O(k) each time).
  • Calling list.index, x in list or list.pop(0) inside a loop: each is O(n). Use a set, a dict or a deque.
  • Ignoring recursion-stack space in DFS (O(h), which can be O(n) for a skewed tree).
Check yourself: what is the complexity of sorting, then doing a binary search for each of n queries? O(n log n) to sort + n × O(log n) for the searches = O(n log n).
Check yourself: n = 2·10⁵. Is an O(n²) solution acceptable? No. 4·10¹⁰ operations is minutes of work. Aim for O(n log n) or O(n).
